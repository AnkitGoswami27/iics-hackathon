2. IICS — Architecture & Key Concepts

What is IICS?

IICS (Informatica Intelligent Cloud Services) is a cloud-native data integration platform (part of IDMC — Informatica Data Management Cloud). It lets you build, run, and manage data pipelines, ETL/ELT jobs, and API integrations without managing on-premise infrastructure.

5. IICS — Interview Questions & Answers

Q1: What is the difference between a Mapping and a Mapping Task in IICS?
A Mapping defines the data flow logic (transformations, source, target). A Mapping Task is the runnable instance of that mapping — it binds the mapping to a Secure Agent, runtime environment, and specific connections. You can have one mapping with multiple mapping tasks pointing to different environments (Dev/QA/Prod).
Q2: What is a Secure Agent and why is it needed?
A Secure Agent is a lightweight software installed on-premises or on a VM in your network. It executes the actual data movement between local sources (Oracle DB, flat files) and the IICS cloud. It establishes an outbound-only HTTPS connection to IICS — no inbound ports are opened, so firewall rules are minimal. It ensures data never leaves your network unencrypted.
Q3: What are the types of Lookup transformations?
Connected Lookup: Part of the main data flow; passes data through it; can return multiple columns; supports dynamic cache (updates during run).
Unconnected Lookup: Called with :LKP.lookup_name() expression; returns a single value; supports static cache only; useful for conditional value lookup without disrupting the main pipeline.
Q4: How do you handle rejected/bad records in IICS?
Use a Router transformation to split data: one group passes valid records to the target, another group routes invalid records (nulls, invalid IDs, out-of-range values) to a REJECTED_RECORDS flat file or error table. Also configure the Error Log at the Mapping Task level for row-level errors. You can set a Stop-on-Error threshold.
Q5: What is the difference between CDI and CAI?
CDI (Cloud Data Integration) = batch ETL/ELT — schedule-driven bulk data movement (e.g., nightly loads). CAI (Cloud Application Integration) = real-time event-driven API integration — REST/SOAP, message queues, process automation triggered by events in milliseconds. Use CDI for warehouse loads; use CAI for live order APIs.
Q6: What is SCD Type 2 and how do you implement it?
SCD Type 2 (Slowly Changing Dimension Type 2) preserves full history by inserting a new row when an attribute changes, marking the old row as expired. In IICS, use: Source → Lookup (check if record exists and if changed) → Router (New / Changed / Unchanged) → Expression (set EFFECTIVE_DATE, END_DATE, IS_CURRENT) → Target (insert new row + update old row).
Q7: How do you pass dynamic values (like today's date) to a mapping?
Use Parameters ($$PARAM_NAME) defined at the Mapping Task or Taskflow level. You can pass a parameter file where $$LOAD_DATE = SYSDATE or a specific date string. Inside the mapping, reference the parameter in Expression transformations: TO_DATE($$LOAD_DATE, 'YYYY-MM-DD').
Q8: What is a Taskflow?
A Taskflow is an orchestration object that sequences and branches multiple Mapping Tasks with control flow logic (sequence, condition, parallel execution, loop, email notification, sub-taskflow). It is IICS's equivalent of a workflow. Example: Load dimensions → wait → load facts → send email on completion.
Q9: How do you run mappings in parallel in IICS?
In a Taskflow, connect tasks from a Start event to multiple tasks simultaneously (fan-out). They will execute in parallel. After all complete, use a Synchronization (AND) gate to merge back before the next sequential task.
Q10: What is pushdown optimization / ELT in IICS?
Pushdown Optimization (PDO) pushes transformation logic down into the database engine (Oracle, Snowflake) as native SQL, so data is not moved to the Secure Agent for processing. This reduces network I/O and leverages the database engine's power. Full pushdown generates a SQL query and executes it on the database; partial pushdown handles unsupported transformations on the agent.

6. SQL Queries — Basic to Advanced

Schema reminder: DIM_CUSTOMERS (CUSTOMER_ID, CUSTOMER_NAME, CITY, STATE), DIM_PRODUCTS (PRODUCT_ID, PRODUCT_NAME, CATEGORY, UNIT_PRICE, STOCK_QTY), DIM_ORDERS (ORDER_ID, CUSTOMER_ID, ORDER_DATE, STATUS, PAYMENT_MODE, TOTAL_AMOUNT), FACT_SALES (FACT_ID, ORDER_ID, PRODUCT_ID, CUSTOMER_ID, TRANSACTION_DATE, QUANTITY, UNIT_PRICE, DISCOUNT_PCT, REVENUE)

Basic Queries

-- 1. All completed orders
SELECT ORDER_ID, CUSTOMER_ID, TOTAL_AMOUNT
FROM   DIM_ORDERS
WHERE  STATUS = 'COMPLETED'
ORDER BY TOTAL_AMOUNT DESC;

-- 2. Products with price above category average
SELECT PRODUCT_NAME, CATEGORY, UNIT_PRICE
FROM   DIM_PRODUCTS
WHERE  UNIT_PRICE > (SELECT AVG(UNIT_PRICE) FROM DIM_PRODUCTS)
ORDER BY CATEGORY, UNIT_PRICE DESC;

-- 3. Count customers per city
SELECT CITY, STATE, COUNT(*) AS CUSTOMER_COUNT
FROM   DIM_CUSTOMERS
GROUP  BY CITY, STATE
ORDER  BY CUSTOMER_COUNT DESC;

-- 4. Total revenue per product
SELECT P.PRODUCT_NAME, P.CATEGORY,
       SUM(F.REVENUE)   AS TOTAL_REVENUE,
       SUM(F.QUANTITY)  AS TOTAL_QTY_SOLD
FROM   FACT_SALES F
JOIN   DIM_PRODUCTS P ON F.PRODUCT_ID = P.PRODUCT_ID
GROUP  BY P.PRODUCT_NAME, P.CATEGORY
ORDER  BY TOTAL_REVENUE DESC;

JOIN Queries

-- 5. Full customer purchase summary
SELECT C.CUSTOMER_NAME, C.CITY, C.STATE,
       COUNT(DISTINCT F.ORDER_ID)  AS TOTAL_ORDERS,
       SUM(F.REVENUE)              AS TOTAL_REVENUE,
       AVG(F.DISCOUNT_PCT)         AS AVG_DISCOUNT
FROM   FACT_SALES F
JOIN   DIM_CUSTOMERS C ON F.CUSTOMER_ID = C.CUSTOMER_ID
GROUP  BY C.CUSTOMER_NAME, C.CITY, C.STATE
ORDER  BY TOTAL_REVENUE DESC;

-- 6. Order details with customer and product info
SELECT O.ORDER_ID, C.CUSTOMER_NAME, P.PRODUCT_NAME,
       P.CATEGORY, F.QUANTITY, F.UNIT_PRICE,
       F.DISCOUNT_PCT, F.REVENUE, O.STATUS, O.PAYMENT_MODE
FROM   FACT_SALES F
JOIN   DIM_CUSTOMERS C ON F.CUSTOMER_ID = C.CUSTOMER_ID
JOIN   DIM_PRODUCTS  P ON F.PRODUCT_ID  = P.PRODUCT_ID
JOIN   DIM_ORDERS    O ON F.ORDER_ID    = O.ORDER_ID
ORDER  BY F.TRANSACTION_DATE DESC;

-- 7. Customers who never placed a COMPLETED order (LEFT JOIN anti-join)
SELECT C.CUSTOMER_ID, C.CUSTOMER_NAME
FROM   DIM_CUSTOMERS C
LEFT   JOIN DIM_ORDERS O ON C.CUSTOMER_ID = O.CUSTOMER_ID
                        AND O.STATUS = 'COMPLETED'
WHERE  O.ORDER_ID IS NULL;

Aggregation & GROUP BY / HAVING

-- 8. Categories with total revenue > 100000
SELECT P.CATEGORY,
       COUNT(F.FACT_ID)   AS TRANSACTIONS,
       SUM(F.REVENUE)     AS TOTAL_REVENUE,
       ROUND(AVG(F.REVENUE), 2) AS AVG_REVENUE
FROM   FACT_SALES F
JOIN   DIM_PRODUCTS P ON F.PRODUCT_ID = P.PRODUCT_ID
GROUP  BY P.CATEGORY
HAVING SUM(F.REVENUE) > 100000
ORDER  BY TOTAL_REVENUE DESC;

-- 9. Monthly revenue trend
SELECT TO_CHAR(TRANSACTION_DATE, 'YYYY-MM') AS MONTH,
       COUNT(*)               AS TRANSACTIONS,
       SUM(REVENUE)           AS MONTHLY_REVENUE
FROM   FACT_SALES
GROUP  BY TO_CHAR(TRANSACTION_DATE, 'YYYY-MM')
ORDER  BY MONTH;

-- 10. Revenue with ROLLUP (subtotals per category + grand total)
SELECT P.CATEGORY, P.PRODUCT_NAME, SUM(F.REVENUE) AS TOTAL_REV
FROM   FACT_SALES F
JOIN   DIM_PRODUCTS P ON F.PRODUCT_ID = P.PRODUCT_ID
GROUP  BY ROLLUP(P.CATEGORY, P.PRODUCT_NAME)
ORDER  BY P.CATEGORY NULLS LAST, P.PRODUCT_NAME NULLS LAST;

Subqueries & Correlated Subqueries

-- 11. Top-spending customer per city
SELECT CITY, CUSTOMER_NAME, TOTAL_REV
FROM (
  SELECT C.CITY, C.CUSTOMER_NAME,
         SUM(F.REVENUE) AS TOTAL_REV,
         RANK() OVER (PARTITION BY C.CITY ORDER BY SUM(F.REVENUE) DESC) AS RNK
  FROM   FACT_SALES F
  JOIN   DIM_CUSTOMERS C ON F.CUSTOMER_ID = C.CUSTOMER_ID
  GROUP  BY C.CITY, C.CUSTOMER_NAME
)
WHERE RNK = 1;

-- 12. Products not sold in the last 90 days (correlated subquery)
SELECT PRODUCT_ID, PRODUCT_NAME, CATEGORY
FROM   DIM_PRODUCTS P
WHERE  NOT EXISTS (
  SELECT 1 FROM FACT_SALES F
  WHERE  F.PRODUCT_ID = P.PRODUCT_ID
  AND    F.TRANSACTION_DATE >= SYSDATE - 90
);

Analytic / Window Functions

-- 13. Running total of revenue ordered by date
SELECT TRANSACTION_DATE, REVENUE,
       SUM(REVENUE) OVER (ORDER BY TRANSACTION_DATE
                          ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS RUNNING_TOTAL
FROM   FACT_SALES
ORDER  BY TRANSACTION_DATE;

-- 14. Rank products by revenue within each category
SELECT P.CATEGORY, P.PRODUCT_NAME,
       SUM(F.REVENUE) AS TOTAL_REV,
       RANK()     OVER (PARTITION BY P.CATEGORY ORDER BY SUM(F.REVENUE) DESC) AS RANK_IN_CAT,
       DENSE_RANK() OVER (PARTITION BY P.CATEGORY ORDER BY SUM(F.REVENUE) DESC) AS DENSE_RANK_IN_CAT
FROM   FACT_SALES F
JOIN   DIM_PRODUCTS P ON F.PRODUCT_ID = P.PRODUCT_ID
GROUP  BY P.CATEGORY, P.PRODUCT_NAME;

-- 15. Compare each sale revenue vs. previous sale (LAG)
SELECT FACT_ID, TRANSACTION_DATE, REVENUE,
       LAG(REVENUE, 1, 0) OVER (ORDER BY TRANSACTION_DATE) AS PREV_REVENUE,
       REVENUE - LAG(REVENUE, 1, 0) OVER (ORDER BY TRANSACTION_DATE) AS REVENUE_DIFF
FROM   FACT_SALES
ORDER  BY TRANSACTION_DATE;

-- 16. Percentage of total revenue per product
SELECT P.PRODUCT_NAME,
       SUM(F.REVENUE) AS PROD_REVENUE,
       ROUND(SUM(F.REVENUE) / SUM(SUM(F.REVENUE)) OVER () * 100, 2) AS PCT_OF_TOTAL
FROM   FACT_SALES F
JOIN   DIM_PRODUCTS P ON F.PRODUCT_ID = P.PRODUCT_ID
GROUP  BY P.PRODUCT_NAME
ORDER  BY PROD_REVENUE DESC;

-- 17. ROW_NUMBER to deduplicate (keep latest per customer per product)
SELECT * FROM (
  SELECT F.*,
         ROW_NUMBER() OVER (PARTITION BY CUSTOMER_ID, PRODUCT_ID
                            ORDER BY TRANSACTION_DATE DESC) AS RN
  FROM FACT_SALES F
)
WHERE RN = 1;

Advanced — MERGE (Upsert)

-- 18. MERGE upsert into DIM_CUSTOMERS from staging
MERGE INTO DIM_CUSTOMERS tgt
USING STAGING_CUSTOMERS src
ON (tgt.CUSTOMER_ID = src.CUSTOMER_ID)
WHEN MATCHED THEN
  UPDATE SET tgt.CUSTOMER_NAME = src.CUSTOMER_NAME,
             tgt.EMAIL         = src.EMAIL,
             tgt.PHONE         = src.PHONE,
             tgt.CITY          = src.CITY
WHEN NOT MATCHED THEN
  INSERT (CUSTOMER_ID, CUSTOMER_NAME, EMAIL, PHONE, CITY, STATE, COUNTRY, CREATED_DATE)
  VALUES (src.CUSTOMER_ID, src.CUSTOMER_NAME, src.EMAIL, src.PHONE,
          src.CITY, src.STATE, src.COUNTRY, SYSDATE);

7. PL/SQL — Procedures, Functions, Cursors, Exceptions

7.1 Stored Procedure — Load FACT_SALES

CREATE OR REPLACE PROCEDURE p_load_fact_sales (
    p_load_date   IN DATE     DEFAULT SYSDATE,
    p_rows_loaded OUT NUMBER
) AS
    v_count  NUMBER := 0;
    v_err_msg VARCHAR2(500);
BEGIN
    -- Insert from staging to FACT_SALES
    INSERT INTO FACT_SALES (
        FACT_ID, ORDER_ID, PRODUCT_ID, CUSTOMER_ID,
        TRANSACTION_DATE, QUANTITY, UNIT_PRICE, DISCOUNT_PCT, REVENUE, LOAD_DATE
    )
    SELECT
        'F' || LPAD(FACT_SEQ.NEXTVAL, 4, '0'),
        s.ORDER_ID, s.PRODUCT_ID, s.CUSTOMER_ID,
        TO_DATE(s.TRANSACTION_DATE, 'YYYY-MM-DD'),
        s.QUANTITY, s.UNIT_PRICE, s.DISCOUNT_PCT,
        ROUND(s.QUANTITY * s.UNIT_PRICE * (1 - s.DISCOUNT_PCT / 100), 2),
        p_load_date
    FROM STG_FACT_SALES s
    WHERE NOT EXISTS (
        SELECT 1 FROM FACT_SALES f WHERE f.FACT_ID = s.FACT_ID
    );

    v_count := SQL%ROWCOUNT;
    COMMIT;
    p_rows_loaded := v_count;
    DBMS_OUTPUT.PUT_LINE('Loaded: ' || v_count || ' rows.');

EXCEPTION
    WHEN OTHERS THEN
        ROLLBACK;
        v_err_msg := SQLERRM;
        INSERT INTO ETL_ERROR_LOG (PROC_NAME, ERROR_MSG, ERROR_DATE)
        VALUES ('p_load_fact_sales', v_err_msg, SYSDATE);
        COMMIT;
        RAISE;
END p_load_fact_sales;

7.2 Function — Calculate Net Revenue

CREATE OR REPLACE FUNCTION f_net_revenue (
    p_quantity      IN NUMBER,
    p_unit_price    IN NUMBER,
    p_discount_pct  IN NUMBER
) RETURN NUMBER IS
    v_net_rev NUMBER;
BEGIN
    IF p_quantity IS NULL OR p_unit_price IS NULL THEN
        RETURN 0;
    END IF;
    v_net_rev := p_quantity * p_unit_price
                 * (1 - NVL(p_discount_pct, 0) / 100);
    RETURN ROUND(v_net_rev, 2);
EXCEPTION
    WHEN ZERO_DIVIDE THEN
        RETURN 0;
    WHEN OTHERS THEN
        RETURN NULL;
END f_net_revenue;
/

-- Usage:
SELECT ORDER_ID, f_net_revenue(QUANTITY, UNIT_PRICE, DISCOUNT_PCT) AS NET_REV
FROM   FACT_SALES;

7.3 Explicit Cursor — Report Top Customers

DECLARE
    CURSOR c_top_customers IS
        SELECT C.CUSTOMER_NAME, C.CITY,
               SUM(F.REVENUE) AS TOTAL_REV,
               COUNT(DISTINCT F.ORDER_ID) AS ORDER_COUNT
        FROM   FACT_SALES F
        JOIN   DIM_CUSTOMERS C ON F.CUSTOMER_ID = C.CUSTOMER_ID
        GROUP  BY C.CUSTOMER_NAME, C.CITY
        HAVING SUM(F.REVENUE) >
               (SELECT AVG(rev_sum) FROM
                  (SELECT SUM(REVENUE) AS rev_sum FROM FACT_SALES
                   GROUP BY CUSTOMER_ID))
        ORDER  BY TOTAL_REV DESC;

    r_cust c_top_customers%ROWTYPE;
BEGIN
    DBMS_OUTPUT.PUT_LINE(RPAD('Customer', 20) || RPAD('City', 15)
                         || LPAD('Revenue', 12) || LPAD('Orders', 8));
    DBMS_OUTPUT.PUT_LINE(RPAD('-', 55, '-'));

    OPEN c_top_customers;
    LOOP
        FETCH c_top_customers INTO r_cust;
        EXIT WHEN c_top_customers%NOTFOUND;
        DBMS_OUTPUT.PUT_LINE(
            RPAD(r_cust.CUSTOMER_NAME, 20) ||
            RPAD(r_cust.CITY, 15) ||
            LPAD(TO_CHAR(r_cust.TOTAL_REV, '999,999.99'), 12) ||
            LPAD(r_cust.ORDER_COUNT, 8)
        );
    END LOOP;
    CLOSE c_top_customers;
    DBMS_OUTPUT.PUT_LINE('Total rows: ' || c_top_customers%ROWCOUNT);
END;
/

7.5 Exception Handling — Named + User-Defined

DECLARE
    v_total_rev  NUMBER;
    v_cust_id    DIM_CUSTOMERS.CUSTOMER_ID%TYPE := '&CUSTOMER_ID';

    -- User-defined exception
    e_customer_not_found EXCEPTION;
    PRAGMA EXCEPTION_INIT(e_customer_not_found, -20001);

BEGIN
    -- Check if customer exists
    SELECT COUNT(*) INTO v_total_rev
    FROM   DIM_CUSTOMERS
    WHERE  CUSTOMER_ID = v_cust_id;

    IF v_total_rev = 0 THEN
        RAISE_APPLICATION_ERROR(-20001, 'Customer not found: ' || v_cust_id);
    END IF;

    -- Get total revenue
    SELECT SUM(REVENUE) INTO v_total_rev
    FROM   FACT_SALES
    WHERE  CUSTOMER_ID = v_cust_id;

    IF v_total_rev IS NULL THEN
        DBMS_OUTPUT.PUT_LINE('Customer has no sales.');
    ELSE
        DBMS_OUTPUT.PUT_LINE('Total Revenue: ' || v_total_rev);
    END IF;

EXCEPTION
    WHEN e_customer_not_found THEN
        DBMS_OUTPUT.PUT_LINE('ERROR: ' || SQLERRM);
    WHEN NO_DATA_FOUND THEN
        DBMS_OUTPUT.PUT_LINE('No data found for this customer.');
    WHEN OTHERS THEN
        DBMS_OUTPUT.PUT_LINE('Unexpected error: ' || SQLCODE || ' - ' || SQLERRM);
        ROLLBACK;
END;

7.6 Bulk Collect + FORALL (Performance)

DECLARE
    TYPE t_fact_tab  IS TABLE OF FACT_SALES%ROWTYPE;
    v_facts          t_fact_tab;
    c_limit          CONSTANT PLS_INTEGER := 1000;

    CURSOR c_stg IS
        SELECT * FROM STG_FACT_SALES;
BEGIN
    OPEN c_stg;
    LOOP
        -- Bulk fetch 1000 rows at a time
        FETCH c_stg BULK COLLECT INTO v_facts LIMIT c_limit;
        EXIT WHEN v_facts.COUNT = 0;

        -- Bulk insert
        FORALL i IN 1 .. v_facts.COUNT
            INSERT INTO FACT_SALES VALUES v_facts(i);

        COMMIT;
    END LOOP;
    CLOSE c_stg;
    DBMS_OUTPUT.PUT_LINE('Bulk load complete.');
EXCEPTION
    WHEN OTHERS THEN
        ROLLBACK;
        RAISE;
END;
/
Performance tip: BULK COLLECT + FORALL reduces context switches between PL/SQL and SQL engine — typically 10–100x faster than row-by-row processing.

8.1 BEFORE INSERT Trigger — Auto-generate FACT_ID

CREATE OR REPLACE TRIGGER trg_fact_sales_bi
BEFORE INSERT ON FACT_SALES
FOR EACH ROW
BEGIN
    IF :NEW.FACT_ID IS NULL THEN
        :NEW.FACT_ID := 'F' || LPAD(FACT_SEQ.NEXTVAL, 4, '0');
    END IF;
    :NEW.LOAD_DATE := SYSDATE;
END;

8.2 AFTER UPDATE Trigger — Audit Trail

CREATE TABLE FACT_SALES_AUDIT (
    AUDIT_ID     NUMBER GENERATED ALWAYS AS IDENTITY,
    FACT_ID      VARCHAR2(10),
    OLD_REVENUE  NUMBER,
    NEW_REVENUE  NUMBER,
    CHANGED_BY   VARCHAR2(50),
    CHANGED_ON   DATE
);

CREATE OR REPLACE TRIGGER trg_fact_sales_au
AFTER UPDATE OF REVENUE ON FACT_SALES
FOR EACH ROW
WHEN (OLD.REVENUE != NEW.REVENUE)
BEGIN
    INSERT INTO FACT_SALES_AUDIT
        (FACT_ID, OLD_REVENUE, NEW_REVENUE, CHANGED_BY, CHANGED_ON)
    VALUES
        (:OLD.FACT_ID, :OLD.REVENUE, :NEW.REVENUE, USER, SYSDATE);
END;
/

8.3 INSTEAD OF Trigger — Updatable View

-- Complex view (not updatable directly)
CREATE OR REPLACE VIEW v_sales_detail AS
    SELECT F.FACT_ID, C.CUSTOMER_NAME, P.PRODUCT_NAME,
           F.QUANTITY, F.REVENUE
    FROM   FACT_SALES F
    JOIN   DIM_CUSTOMERS C ON F.CUSTOMER_ID = C.CUSTOMER_ID
    JOIN   DIM_PRODUCTS  P ON F.PRODUCT_ID  = P.PRODUCT_ID;

-- Make it updatable via INSTEAD OF trigger
CREATE OR REPLACE TRIGGER trg_v_sales_detail_iu
INSTEAD OF UPDATE ON v_sales_detail
FOR EACH ROW
BEGIN
    UPDATE FACT_SALES
    SET    QUANTITY = :NEW.QUANTITY,
           REVENUE  = :NEW.REVENUE
    WHERE  FACT_ID  = :OLD.FACT_ID;
END;
/

8.4 AFTER DELETE Trigger — Prevent Deletion of COMPLETED Orders

CREATE OR REPLACE TRIGGER trg_orders_ad
BEFORE DELETE ON DIM_ORDERS
FOR EACH ROW
BEGIN
    IF :OLD.STATUS = 'COMPLETED' THEN
        RAISE_APPLICATION_ERROR(-20010,
            'Cannot delete a COMPLETED order: ' || :OLD.ORDER_ID);
    END IF;
END;

-- ============= PACKAGE SPECIFICATION =============
CREATE OR REPLACE PACKAGE pkg_retail_etl AS

    -- Public constants
    c_max_discount  CONSTANT NUMBER := 30;

    -- Public types
    TYPE t_revenue_tab IS TABLE OF NUMBER INDEX BY PLS_INTEGER;

    PROCEDURE p_load_customers (p_rows OUT NUMBER);
    PROCEDURE p_load_products  (p_rows OUT NUMBER);

/

-- ============= PACKAGE BODY =============
CREATE OR REPLACE PACKAGE BODY pkg_retail_etl AS

    -- Private helper
    PROCEDURE log_message(p_msg IN VARCHAR2) IS
    BEGIN
        DBMS_OUTPUT.PUT_LINE('[' || TO_CHAR(SYSDATE,'HH24:MI:SS') || '] ' || p_msg);
    END;

    PROCEDURE p_load_customers(p_rows OUT NUMBER) IS
    BEGIN
        MERGE INTO DIM_CUSTOMERS tgt
        USING STG_CUSTOMERS src ON (tgt.CUSTOMER_ID = src.CUSTOMER_ID)
        WHEN MATCHED THEN
            UPDATE SET tgt.CUSTOMER_NAME = src.CUSTOMER_NAME,
                       tgt.EMAIL = src.EMAIL
        WHEN NOT MATCHED THEN
            INSERT VALUES (src.CUSTOMER_ID, src.CUSTOMER_NAME, src.EMAIL,
                           src.PHONE, src.CITY, src.STATE, src.COUNTRY, SYSDATE);
        p_rows := SQL%ROWCOUNT;
        COMMIT;
        log_message('Customers loaded: ' || p_rows);
    END;

    FUNCTION f_customer_revenue(p_cust_id IN VARCHAR2) RETURN NUMBER IS
        v_rev NUMBER;
    BEGIN
        SELECT NVL(SUM(REVENUE), 0) INTO v_rev
        FROM   FACT_SALES
        WHERE  CUSTOMER_ID = p_cust_id;
        RETURN v_rev;
    EXCEPTION
        WHEN NO_DATA_FOUND THEN RETURN 0;
    END;

    PROCEDURE p_run_full_pipeline IS
        v_r NUMBER;
    BEGIN
        log_message('Pipeline start');
        p_load_customers(v_r);
        p_load_products(v_r);
        p_load_fact_sales(SYSDATE, v_r);
        log_message('Pipeline complete');
    EXCEPTION
        WHEN OTHERS THEN
            log_message('Pipeline FAILED: ' || SQLERRM);
            RAISE;
    END;

END pkg_retail_etl;
/

10. PL/SQL — Interview Questions & Answers

Q1: What is the difference between a Procedure and a Function?
A Function must return a value; a Procedure may use OUT/IN OUT parameters but does not use RETURN to send back a value. Functions can be used in SQL expressions (SELECT, WHERE); procedures cannot. Both can have IN/OUT parameters.
Q2: What is %TYPE and %ROWTYPE?
%TYPE inherits the datatype of a single column: v_name DIM_CUSTOMERS.CUSTOMER_NAME%TYPE. %ROWTYPE inherits the structure of an entire row: v_cust DIM_CUSTOMERS%ROWTYPE. Both ensure variables stay in sync if the table definition changes — no manual datatype maintenance.
Q3: Implicit vs Explicit Cursor — when to use which?
Implicit cursor is automatically created for every DML statement and single-row SELECT INTO. Use it for simple one-row queries. Explicit cursor must be declared, opened, fetched, and closed. Use it for multi-row result sets where you need row-by-row processing or fine-grained control. Cursor FOR loops are a clean shorthand for explicit cursors.
Q4: What is BULK COLLECT and FORALL? Why use them?
Normal cursor loops cause a context switch between PL/SQL and SQL engine for every row — O(n) context switches. BULK COLLECT fetches multiple rows into a collection in one SQL call. FORALL sends all DML statements to the SQL engine in one batch. Together they dramatically reduce context switches — 10–100x performance improvement for large datasets.
Q5: What is PRAGMA EXCEPTION_INIT?
It associates a named PL/SQL exception with an Oracle error number: PRAGMA EXCEPTION_INIT(e_fk_violation, -2291);. This lets you catch specific Oracle errors by a meaningful name instead of using WHEN OTHERS and checking SQLCODE.
Q6: Difference between COMMIT, ROLLBACK, SAVEPOINT?
COMMIT permanently saves all changes since the last commit. ROLLBACK undoes all changes since the last commit. SAVEPOINT sp1 marks a point; ROLLBACK TO sp1 undoes only changes after that savepoint, preserving earlier changes. DDL (CREATE, ALTER) auto-commits in Oracle.
Q7: What is an INSTEAD OF trigger?
A trigger fired instead of the DML on a view. Since complex views (multi-table joins, GROUP BY, DISTINCT) are not directly updatable, an INSTEAD OF trigger intercepts the DML and translates it into DML on the underlying base tables.
Q8: What is the difference between DELETE and TRUNCATE?
DELETE is DML — can be rolled back, fires triggers, logs every row deletion, can use WHERE clause. TRUNCATE is DDL — auto-commits, cannot be rolled back (in most cases), does NOT fire row-level triggers, much faster on large tables, resets HWM (High Water Mark).
Q9: What are Oracle Supplied Packages you use regularly?
DBMS_OUTPUT — debug print to console.
DBMS_JOB / DBMS_SCHEDULER — schedule PL/SQL jobs.
UTL_FILE — read/write OS files from PL/SQL.
DBMS_METADATA — extract DDL of objects.
DBMS_STATS — gather optimizer statistics.
UTL_HTTP / UTL_SMTP — HTTP calls, send email from Oracle.
Q10: How do you handle exceptions in a package?
Each procedure/function in the package body has its own EXCEPTION block. Errors can be logged to an error table, re-raised using RAISE, or converted using RAISE_APPLICATION_ERROR. Package-level variables can hold error state for the session. Always ensure COMMIT/ROLLBACK are called correctly before raising.
SECTION 5 — PRESENTATION Q&A

11. Presentation Questions & Model Answers

Q: Walk us through your data pipeline architecture.
"We have a retail data warehouse pipeline. Source data — customers, products, orders, and sales transactions — arrives as flat CSV files. These are ingested into Oracle staging tables using IICS CDI mappings. We then apply transformations: data cleansing (null checks, duplicate removal, format standardization), and lookups to enrich the fact data with dimension keys. The clean data flows into a Star Schema — one FACT_SALES table and three dimension tables. The entire pipeline is orchestrated by an IICS Taskflow that loads dimensions first (in parallel) and then loads the fact table, with error routing to a rejected-records file and email alerts on completion or failure."
Q: Why did you choose a Star Schema instead of a normalized model?
"Star schema is optimized for analytical queries — fast aggregations, fewer JOINs, easy for BI tools to query. A fully normalized model is better for OLTP (transactions), but in our warehouse use case, we need fast reads for reporting. The denormalization trade-off (some redundancy) is acceptable for the performance gains."
Q: How do you handle dirty / bad data?
"In IICS, we have a Filter transformation that checks for null CUSTOMER_ID, null PRODUCT_ID, zero or negative quantities, and invalid dates. Records failing these checks are routed by the Router transformation to a REJECTED_RECORDS target file, while clean records proceed to FACT_SALES. We track rejection count per batch and alert if it exceeds a configured threshold."
Q: What is the difference between your current pipeline and SCD Type 2?
"Our current pipeline does a simple MERGE upsert — if a customer record changes, we overwrite it (SCD Type 1 — no history). SCD Type 2 would insert a new row for every change, preserving history with EFFECTIVE_DATE and END_DATE columns. We would use SCD Type 2 if the business needed to report on what a customer's address was at the time of a historical order, for example."
Q: How would you scale this pipeline for 10 million records/day?
"We would use IICS Mass Ingestion for parallel file loading, enable Pushdown Optimization so transformations run inside Oracle, use Bulk Collect + FORALL in PL/SQL for post-load processing, partition the FACT_SALES table by TRANSACTION_DATE (range partitioning), add bitmap indexes on dimension foreign keys, and scale horizontally by adding more Secure Agent nodes for parallel partition processing."
Q: What monitoring do you have for the pipeline?
"In IICS, every job execution is visible in the Monitor tab — status (success/running/failed), rows processed, rows rejected, and detailed session logs. We also maintain an ETL_ERROR_LOG table inside Oracle for procedure-level errors. The Taskflow sends email notifications on success or failure. For production, we'd integrate with an alerting tool (PagerDuty, ServiceNow)."
